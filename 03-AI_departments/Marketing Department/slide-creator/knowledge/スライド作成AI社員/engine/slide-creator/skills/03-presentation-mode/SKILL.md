# presentation-mode — 登壇プレゼン特化スキル

**配布資料ではなく、登壇して声で語るプレゼン**に特化したHTMLスライド制作スキル。
1スライド1メッセージを徹底し、ビジュアルと余白で「見せる」デッキを作る。

## プレゼンモードの設計原則

### 1スライド1メッセージの鉄則

- **1枚に伝えたいことは1つだけ**。2つ以上のメッセージが入っていたらスライドを分割する
- 見出しは「カテゴリ名」ではなく「主張文」にする（NG: `AIの特徴` → OK: `AIは24時間働くもう一人のマーケター`）
- 聴衆が見出しだけ読んで主張を理解できるか？ が判定基準

### 文字量の制約（配布資料と明確に違う点）

| 要素 | プレゼンモード | 配布モード（参考） |
|---|---|---|
| 1スライドの最大文字数 | **60文字** | 180文字 |
| 箇条書き最大項目数 | **3項目** | 5項目 |
| 1行の最大文字数 | **20文字** | 30文字 |
| 見出しフォント | **大（基準の×2.2）** | 標準（基準の×1.6） |
| 本文フォント | **大（キャンバス短辺の約3.3%cqw）** | 縮小（約2.2%cqw） |
| ビジュアル比率 | **60%以上** | 40%以上 |

### ビジュアルファースト

- 各スライドの60%以上を画像・図解・写真・余白で占める
- テキスト箇条書きだけのスライドは全体の30%以下にする
- **Unsplash のスタイリッシュな写真**をフル活用する（詳細は `../../knowledge/references/html-slide-unsplash-guide.md`）
- ブランド アセット（`<社内ナレッジ>/株式会社アイウエオ/assets/img/`）の実写・イラストも積極的に使う

### 余白の使い方

- **余白は情報**。余白が多いほどメッセージが強くなる
- ステートメント型（§G / F1）では画面の70%以上を余白にしてよい
- 箇条書き間の行間は本文の2倍以上空ける
- セーフティマージン80pxを超えて攻めない

## スライド構成の型（プレゼン向き）

プレゼンでは以下のストーリー構造を基本にする:

```
問い → 共感 → 発見 → 納得 → 行動
```

### 推奨構成（15〜25枚の標準デッキ）

| # | 役割 | 推奨レイアウト | 枚数目安 |
|---|------|---------------|---------|
| 1 | 表紙 | 左右分割（右に Unsplash フルブリード写真） | 1枚 |
| 2 | AGENDA | 標準 AGENDA テンプレ | 1枚 |
| 3 | 問いかけ | §G ステートメント（ダーク全面 + 一行の問い） | 1枚 |
| 4-5 | 共感・問題提起 | §C Before/After / §4 画像左+テキスト | 2枚 |
| 6 | セクション扉 | 標準セクション扉 | 1枚 |
| 7-10 | 解決策・核心 | §A プロセス / §B 3カード / §O アイコンリスト / Unsplash フル写真 | 3-4枚 |
| 11 | ブリッジ | §G ステートメント（中間CTA: 「今日からできること」） | 1枚 |
| 12 | セクション扉 | 標準セクション扉 | 1枚 |
| 13-16 | 証拠・事例 | §L メトリクス / §F 引用 / §M ギャラリー / §H X グリッド | 3-4枚 |
| 17 | セクション扉 | 標準セクション扉 | 1枚 |
| 18-20 | 行動喚起 | §S ステップカード / §N ファネル / §T CTA クロージング | 2-3枚 |

### スライド間のリズムルール

- **3枚連続で同じレイアウトにしない**（5枚禁止ルールよりさらに厳しく）
- **テキスト主体スライドの後には必ずビジュアル主体スライドを入れる**
- セクション間のブリッジには §G ステートメントか **Unsplash フルブリード写真 + 短い一文** を使う
- 数字を見せた後は、その数字が意味する「人の変化」を写真で見せる

## Unsplash 画像の活用ポイント（プレゼンモード固有）

**詳細なルールは `../../knowledge/references/html-slide-unsplash-guide.md` を参照。** ここではプレゼン特有のポイントのみ:

### 使うべき場面

| 場面 | 使い方 | 例 |
|------|--------|-----|
| **表紙の右半分** | フルブリード（`background-size: cover`） | オフィス・テクノロジー・チーム |
| **ステートメントの背景** | ダークオーバーレイ（`rgba(26,26,46,0.75)`）越し | 抽象テクスチャ・都市夜景 |
| **セクション切り替え** | フルスクリーン + 中央に白文字 | ミニマルな風景・パターン |
| **事例・ストーリー** | §4 / §P の画像パネル | 働く人・ワークスペース |
| **感情喚起** | F5 イメージフル（80%以上） | 自然・光・質感 |

### 使わないほうがいい場面

- データ・数字が主役のスライド（§L メトリクス、§E 5理由）→ 数字を邪魔する
- プロセス・フロー（§A、§S）→ 図解が主役
- ロゴウォール（§R）→ ロゴ画像が主役

## トークスクリプト（data-notes）

プレゼンモードでは **全スライドに data-notes を必ず付ける**。

| 項目 | 基準 |
|---|---|
| 文字数 | 150〜300文字（60〜120秒分） |
| 文体 | 口語体（〜です、〜ます、〜ですよね） |
| 構成 | ①このスライドで言いたいこと1文 → ②補足2〜3文 → ③次への橋渡し1文 |
| ビジュアルへの言及 | 「この写真を見てください」「右の図のとおり」など指す言葉を入れる |
| 禁止 | スライドのテキストをそのまま読む / 体言止めのメモ書き |

## 実行手順

1. インテークで brief を揃える
2. ストーリー構造（問い→共感→発見→納得→行動）に沿って構成案を作る
3. 各スライドに **1メッセージ + レイアウト型 + ビジュアル方針（Unsplash キーワード / ブランド アセット名）** を付ける
4. 構成承認ドラフトを提示（承認前に HTML を書かない）
5. 承認後、HTML/CSS/JS を生成
6. Unsplash 画像は `<img>` の `src` または CSS `background-image` で直リンク（`https://images.unsplash.com/...`）
7. ブランド アセットは `assets/` にコピーして使う
8. 全スライドに `data-notes`（トークスクリプト）を付与
9. validator + 目視で品質チェック

## HTML表示事故の再発防止（必須）

過去のセミナーの AIツール × ナレッジ管理 デッキで発生した「横送り/リロードで一部スライドが白・黒・画面外になる」事故を再発させない。

### 絶対ルール

- **スライドrootの位置は最後に強制する**。テンプレ root が `.tpl-bigword`, `.tpl-state`, `.tpl-bio-detail` 等で `position:relative` を持つと、`.slide{position:absolute}` が同 specificity で負け、active slide が通常フローで下に積まれて画面外へ落ちる。必ず CSS 末尾に以下を入れる。

```css
body:not(.grid-view) .stage > .slide {
  position: absolute !important;
  top: 50% !important;
  left: 50% !important;
  transform: translate(-50%, -50%) !important;
}
```

- **背景色の保険に `background:` shorthand を使わない**。`background:#fff !important` は `background-image` も消す。背景画像を残すため、保険は必ず `background-color:#fff !important` にする。
- `opts.bg` / 写真背景を JS で入れる場合、`setAttribute('style', ...)` の後で画像指定を消さない。`background-image`, `background-size`, `background-position` を最後に `style.setProperty(..., 'important')` で再指定する。
- CSS/JS を修正したら `index.html` の `?v=N` を必ず上げる。Chrome/iCloud/ローカルキャッシュで旧CSSが残ると、直したのに直っていないように見える。
- 写真背景スライドは近傍だけでなく、初期表示後に全スライドの `background-image` と `<img>` を warm-up/preload する。横送り時の初回描画遅延を潰す。

### 検証ルール

- 問題が出たスライド番号は、Puppeteer/Playwright で `window.app_show(n - 1)` して全件確認する。
- active slide の `getBoundingClientRect()` が `{x:0, y:0, width:viewportWidth, height:viewportHeight}` 付近であることを確認する。`y=720,1440...` なら画面外に落ちている。
- 背景画像スライドは `getComputedStyle(active).backgroundImage` が `none` になっていないことを確認する。
- 代表スライドをスクショで目視確認する。最低でも「人物紹介」「写真背景質問」「bigword」「最後のThank you/ロゴ」を見る。

## 2026-06-01 追加ルール（Week 7 マーケティングフル活用 制作の学び）

実戦投入で得た恒久ルール。次回以降のプレゼンモード作業で**毎回**守る。

### R1. 16:9 を保ちつつ「下白帯」を絶対に出さない

- `body` / `.stage` の **背景色は `var(--c-dark)` 等の暗色**。`var(--c-base)` 白にすると letterbox が白帯として目立つ。
- **navbar は overlay 式**にする（`position:fixed` で stage の高さを食わない）。stage は `height: 100vh` を丸ごと使う。
- ナビは普段透明、hover or pin で表示する仕様にすると本番投影で邪魔にならない。
- スケール計算は `Math.min(vw/1920, vh/1080)`。`vh - navbar-height` で引き算しない（overlay前提）。

### R2. 文字と装飾の衝突を絶対に出さない

- `tpl-bigword-3d` 系の **タイトルは `max-width: 55〜60%` に厳格制限**、`word-break: keep-all; overflow-wrap: anywhere;` で日本語の折返しを制御。
- 装飾画像・3D形状は **`z-index: 0` で背面化**、テキストは `z-index: 3` で前面。`position: relative` を全部のテキスト要素に書く。
- 装飾のサイズは画面の **右側 50% 以内**に閉じ込め、左側はテキスト専用領域として死守する。
- ロゴが装飾枠内に入るときは画面短辺の **9cqw まで**。`14cqw` は大きすぎてタイトルを侵食する。

### R3. 余白を詰めて、フォントを大きく

- すべての本文系テンプレの **padding は `3〜3.5cqw`** が標準。`5cqw` は広すぎる（90分プレゼンの密度に合わない）。
- 役職カード・組織図のロール名フォントは **`1.2〜1.4cqw` 以上**（`0.95cqw` は読めない）。
- 「下に空白が余って気になる」とユーザーが感じたら、**まず padding 削減 → font 拡大 → コンテンツ追加** の順で詰める。フォントを増やしすぎる前にレイアウトを見直す。
- common shrink rule を CSS 末尾に `!important` で書く: `.tpl-* { padding: 3cqw 3.5cqw !important; }`

### R4. 同じテンプレの連投を禁止する

- ステートメント系 (`tpl-statement-grad` / `tpl-photo-overlay` / `tpl-statement`) は **3枚連続で同じパターンにしない**。背景・色・写真の有無を交互に切り替える。
- 章扉 (`tpl-chapter`) は色味を章ごとにグラデで変える（青系→紫系→暖色→暗色）。
- ブリッジ4-8枚は **写真背景dark / 写真背景light / 純グラデ / グラデ + 装飾** の4種ローテで使う。

### R5. AIツール・SNSロゴを毎スライドに最低1個

- ロゴは **Simple Icons CDN**（`https://cdn.jsdelivr.net/npm/simple-icons@v11/icons/<slug>.svg`）から `curl` でローカル保存。
- **Cursor は Simple Icons に無い**ので、公式の黒キューブロゴPNGを手動取得→ `assets/logos/cursor.png` 配置。
- 表紙とクロージングは **7〜11個のロゴ集合**を低opacityで配置して世界観を提示。
- 各スライドは関連ツールロゴを**最低1個**配置する（X枠ならX、メルマガならGmail等）。

### R6. 写真背景型ステートメントを活用する

- 新規 `tpl-photo-overlay` テンプレ（dark variant / light variant）を **問いかけ・発見・ブリッジ・結論**に積極投入。
- Unsplash 直リンク + `linear-gradient(rgba(26,26,46,.82)..)` で読みやすさ確保。
- ライト版は `rgba(255,255,255,.78)..` の白オーバーレイ + 黒文字、対比のリズムを作る。
- `templates/snippets/` の **§U / §AK / §AL** (既存写真背景パターン) と組み合わせて使う。

### R7. テンプレを「本デッキだけ」に閉じない（重要）

- 本デッキ (`output/archive/<案件>/`) で新規 CSS テンプレを足したら、**必ず同時に**
  - `templates/snippets/` に単体 HTML スニペットを追加（`AM-` `AN-` … の連番）
  - `templates/index.html` のカタログにアイテム追記
- 「本デッキだけ更新／snippetsは古いまま」は禁止。**次回デッキ制作時に同じテンプレが選択肢に出ない**＝資産化されない事故になる。
- Week 7 で追加した §AM〜§AU（statement-grad / chapter / bigword-3d / cardsvis / merge / orgchart / evolution / vscards / dataflow）はこの規律で snippets に同期済み。

### R8. 「全部見えてる？」を毎回チェック

- 90分以上のプレゼンは **48枚程度・1枚 110秒**を目安に組む。
- 受講者が**最後列から読める**フォントサイズかどうかを `cqw` 値で確認（h1 = 4.4+cqw、role名 = 1.2+cqw）。
- 検証: Puppeteer or 手動で全枚スクショ → 16:9 viewport で下白帯・はみ出し・被りをチェック。

### R9. 余白を「永久に」詰める（merge / orgchart / vscards / dataflow 系は特に）

- **本文密度が高いテンプレ** (`.tpl-merge` / `.tpl-orgchart` / `.tpl-vscards` / `.tpl-dataflow`) は **`padding: 2cqw 2.5cqw`** がデフォ。`3cqw` でも余白が目立つ。
- 他の本文系も **`padding: 2.5cqw 3cqw`**。表紙・章扉・statement系だけ `padding: 3〜6cqw` 許容。
- **「下に空白が余る」「文字が小さく見える」**フィードバックが来たら、まず padding 削減 → cqw値 +0.2〜0.3 で対応。
- common shrink を CSS 末尾に `!important` で書く:
  ```css
  .tpl-merge, .tpl-orgchart, .tpl-vscards, .tpl-dataflow { padding: 2cqw 2.5cqw !important; }
  ```

### R10. 全テンプレを ブランド 紫×オレンジグラデで統一する

- 単色（紫だけ・ダークだけ）は使わない。**`--c-gradient: linear-gradient(145deg, #7b6ce0 0%, #9b8cff 24%, #c87941 49%, #e8b88a 74%, #f7f0f6 100%)`** をベースにする。
- ヘッダー（`.tpl-vscards__col-head` / `.tpl-merge__col-head` / `.tpl-orgchart__dept`）は `var(--c-gradient)`。
- アイコン円形（`.tpl-dataflow__node-icon`）は紫起点・オレンジ起点の3バリエでローテ。
- ハブ系（`.tpl-merge__hub`）は **dark→紫→オレンジのグラデ**で見せ場を作る。
- snippet 単体ファイルでも `:root { --c-grad: linear-gradient(...) }` を冒頭で定義してインライン参照する。

### R11. 既存テンプレを「企業デッキ風」だけに偏らせず全種使う

- 同じテンプレ多用は禁止 (R4) と同時に、**「使ってないテンプレが出るのも禁止」**。1デッキで最低 **10〜15種** のテンプレを動員する。
- 用途で使い分け:
  - **自己紹介系** (No.13-15 speakers/bio-detail/bio-team) → AGENDA直後に毎回1枚
  - **実績系** (No.24 xgrid / No.12 stat-bang / No.18 table) → 説得材料として2〜3枚
  - **イラスト系** (No.28 illust-side) → 概念説明に
  - **テーブル** (No.18 table) → MCP対応表・プラン比較
  - **3カード横並び** (No.31 gifts-3) → プレゼント以外でも「3つの特徴」「3つの導線」に汎用可
  - **呼びかけ系** (No.10/11 question-dark/light) → セミナー中の問いかけ
- 「企業デッキっぽい角ばった boxレイアウト」(No.16-23) だけで埋めない。**ステートメント系 (B)・人物紹介 (C)・実績 (G) を必ず混ぜる**。

### R12. テンプレカタログは「通し番号 + カテゴリ分け」を維持

- ファイル名は履歴順 (`01-` `U-` `AA-` `AM-`...) のままでよい。**カタログ表示は No.01〜No.N の通し連番**にする。
- カテゴリは9種（A: 表紙/章扉、B: ワンメッセージ、C: 人物、D: 対比、E: フロー、F: 組織、G: データ、H: 画像、I: CTA）で括る。
- 新規テンプレ追加時は **「カテゴリどこに入るか」を先に決めてから書く**。中途半端なテンプレは作らない。
- カタログ更新は本デッキ更新と**同じコミット**で行う（R7 と合わせて）。

### R13. 「永久テンプレ (eternal/)」と「普通テンプレ (snippets/)」をフォルダで分ける

`templates/` 配下を 2 種類に分ける。混ぜない。

| 種別 | フォルダ | 中身 | 編集 | 使い方 |
|------|----------|------|------|--------|
| **永久テンプレ** | `templates/eternal/` | **完成スライド本体**（過去デッキで投影・好評だったもの） | **触らない**。数字だけ最新に差し替え。レイアウト・装飾・色・文章は変更禁止 | デッキ制作時、骨格にそのまま貼る |
| 普通テンプレ | `templates/snippets/` | 型 (placeholder + 構造) | 文字を毎回差し替える前提 | 内容に合わせて埋めて使う |

#### 何を永久テンプレに入れるか

- **毎回必要な「定番」**（自己紹介・実績紹介・チャネル紹介・表紙ビジュアル等）
- **過去デッキで投影し、受講者の反応が良かった完成品**
- **ゼロから作り直すと品質ブレが起きるもの**

#### 永久テンプレ運用ルール

- レイアウト・色・装飾は **絶対に触らない**（触ったら永久でなくなる）
- 数字 (フォロワー・売上・参加者数) だけ、最新値で **置換のみ** 行う
- 名前・URL・会社名も「変わったときだけ」差し替え。文面のニュアンスは触らない
- 永久テンプレを変えたい時は、**新規 No. を発番して別ファイルで作る**。既存は古い時系列の証拠として残す

#### 表紙ビジュアル固定ルール (EC1)

- **新規デッキの表紙の右ビジュアルは `templates/eternal/assets/cover-hero.png` を毎回使う**。Unsplash 直リンクを毎回別の写真にしない。
- これで全デッキの表紙トーンが揃う。「あの人のスライドだ」と認識される世界観の核になる。
- **ブランド ロゴを表紙左上に重ねない**（小サイズで潰れて読めなくなるため）。ロゴはクロージング (No.34) と章扉のフッターだけに使う。
